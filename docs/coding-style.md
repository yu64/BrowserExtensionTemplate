# コードの書き方の決まり（TypeScript + React）

このプロジェクトのコードは、次の決まりに従って書くこと。決まりには理由を添えてある。迷ったら理由に合うほうを選ぶ。

React を使わない部分では、「React」の節は読み飛ばしてよい。

## コメント・文書
- コメントと文書は日本語で書く。やさしい言葉で、1文に1つのことを書く。
- コメントには「何をするか」に加えて、「なぜそうするか」を書く。
- 説明は実装と合わせる。実装を変えたら、説明も同じ変更で直す。
- JSDoc は、公開していない関数・クラス・部品にも付ける。空の JSDoc は書かない。

## 全体の書き方
- **export は名前付きにする。** default export は、フレームワークが求めるファイル（ルーティングのファイル・設定ファイルなど）だけにする。
- **インラインでない関数は `function` で書く。** `const f = () => {}` の形にしない。（例外はクラスの中。下の「クラス」を見る。）
- **値がないことは `undefined` で表す。** `null` は、DOM・ref・JSON の値・外部の API が返すものに限る。
- **`as`（型の決め打ち）を使わない。** 型安全が前提。型ガードや、値の組み替えで型を絞る。
- **`!`（null でないことの決め打ち）を使わない。** 型で絞り込む。

## ファイル
- 1つのものを表すファイルは PascalCase にする。1つのものとは、コンポーネント・クラスを指す。
- 独立した関数・定数・型の集まりのファイルは camelCase にする。フック（`useXxx`）も関数なので camelCase にする。
- 1ファイルに1コンポーネントにする。そのファイルの中だけで使う小さな部品は、「内部部品」の区分に置いてよい。
- **ファイルを区分に分ける。** 後から足すときに、置き場所が決まるようにするため。区分が1つでも見出しを付ける。

  ```ts
  // #############################################################################
  // MARK: 型定義
  ```

  - 見出しの行は、`// ` の後に `#` を並べ、80文字目で終える。
  - クラスの中などの下の階層は、`// ====…` の行と `// MARK: 名前` にする。
  - 見出しの名前と順番は、次のとおり。
    1. 型定義
    2. 定数
    3. 状態
    4. コンポーネント／フック／関数／クラス（公開するもの）
    5. 内部部品／内部フック／内部関数／内部クラス
    6. 初期化（読み込んだときの副作用）
  - 関数の多いファイルは、内容ごとの名前の見出し（「長さ」「検証」など）でもよい。
  - テストと、再公開だけのファイルは、区分に分けなくてよい。

## React
- React 19 を前提にする。`forwardRef` は使わず、ref は props で受け取る。
- 公開するコンポーネントの引数の型は、`Props` という名前にする（`XxxProps` にしない）。外のパッケージから使う型だけは例外。
- フックの依存の配列をわざと外すときは、`eslint-disable` のコメントに理由を書く。
- **その部品専用の Context・Provider・フックを作らない。** 部品どうしのやり取りは、汎用の仕組み（共有の状態・要求を送る仕組みなど）と props で行う。まとめるだけのフックも作らない。
- **差し替えは `children` で行う。** 組み替えたい部品は、既定の中身を持たせる。使う側が `children` を渡せば、それに置き換わるようにする。
- **JSX の組み立てで済むなら、関数を増やさない。** 例えば「変数のボタン」は、変数から設定を作る関数を外に出さず、元のボタン部品を JSX で包む部品として作る。

## クラス
- **クラスの中の関数は、アロー関数のフィールドにする**（`public get = (): TState => this.#state;`）。メソッドだけを取り出して渡しても、`this` が外れないようにするため。
- **メンバーには、`constructor` も含めて `public`・`private`・`protected` を書く。** 中だけで使うものは `#` にする（`#` には修飾子を書かない）。
- **継承しない。** 組み合わせで作る。アロー関数のフィールドは、継承先で `super.名前()` を呼べないため。
- **型引数は、`T` で始まる2文字以上の名前にする**（`TValue`・`TState` など）。1文字だと、何の型かを覚えておく必要があるため。
- 汎用の仕組みは、「React に依存しないクラス」と、「Provider とフックの一組を作る関数」に分ける。インスタンスは持ち主が作り、Provider は props で受け取って配るだけにする。
- **状態（保存先など）を持つものは、クラスにする。** 状態を中心に関数を並べたモジュールにしない。
- **クラスの定義と、インスタンスの作成を分ける。** インスタンスは使う側（エントリポイントなど）が作り、クラスを定義したファイルでは作らない。定義が使われ方に依存せず、テストでもインスタンスを作り直せるようにするため。React の画面には props で渡す。

## 整形の形
- 字下げはスペース2つにする。
- 波かっこは、次の行に置く（Allman）。`else`・`catch`・`finally` も、`}` の次の行に置く。関数・クラス・アロー関数の本体も同じにする。オブジェクトのかっこは対象外。

  ```ts
  function getSize(vertical: boolean): number
  {
    if(vertical)
    {
      return 15;
    }
    else
    {
      return 60;
    }
  }
  ```

- `if`・`for`・`while`・`switch`・`catch` の後には、空白を入れない（`if(`）。
- if の波かっこは、きわめて単純なときだけ省いてよい。中身が `return`・`continue`・`break`・`throw` の1文で、1行に収まるときに限る。`else` があるときは省かない。

  ```ts
  if(!isRecord(value)) return undefined;
  ```

- 三項演算子は、かっこで囲む。複数行なら `(` の後で改行し、`?` と `:` を行頭に置く。入れ子は、内側もかっこで囲む。

  ```ts
  const size = (
    vertical
    ? 15
    : 60
  );
  ```

- 複数行の三項演算子は、条件が単純な名前（`isHoge`・`!isHoge` など）でなければ、条件もかっこで囲む。
- 三項演算子の枝がオブジェクトなら、短くても複数行にする。
- 型の条件型（`A extends B ? X : Y`）も、三項演算子と同じ形にする。ただし条件をかっこで囲むと構文の誤りになるので、全体だけを囲む。
- オブジェクトは、プロパティが1つなら1行で書く。2つ以上なら、1行に1つずつ書く（分割代入と型は対象外）。

  ```ts
  const a = { x: 1 };
  const b = {
    x: 1,
    y: 2,
  };
  ```

- `&&`・`||` などの演算子は、行頭に置く。
- 型の別名（`type X = …`）の右辺のユニオンは、かっこで囲み、1行に1つずつ `| ` で始めて並べる。2つだけで短くても縦に並べる。ユニオンの中のオブジェクトの型は、プロパティを `,` で区切る。引数や戻り値の中のユニオン（`string | undefined`）は1行のままでよい。

  ```ts
  type State = (
    | { status: "idle" }
    | {
      status: "failed",
      reasons: string[],
    }
  );
  ```

## import
- 型は `import type { ReactNode } from "react"` のように、値とは別の行で読み込む。`React.ReactNode` と書かない。
- 順番は、Node.js の組み込み → パッケージ → `@/`（src からのパス） → 親のフォルダ → 同じフォルダにする。同じまとまりの中は、パスのアルファベット順にする。
- 副作用だけの import（CSS など）は、最後に書く。
- 関数の集まりのモジュール（機能名のモジュール）は、名前空間で読み込む（`import * as i18n from "@/util/i18n"`、`i18n.getMessage(...)`）。どの機能の関数かを、呼び出す側で読めるようにするため。
- コンポーネント・クラス・フックなど、そのものを直接使うときは、名前付き（または default）で読み込む（`import { SettingsStore } from "@/base/SettingsStore"`）。
- import の後には、空行を1行置く。

## 空行
- 空行は、続けて2行まで置いてよい。ファイルの先頭と末尾には置かない。
- `{` の直後と `}` の直前には、空行を置かない。
- **見た目の区切り。** 複数行の文（if・for・try などのブロック、複数行の式・宣言）と、関数・クラス・型の宣言の前後には、空行を置く。大きなまとまりが隣と接して見えて、読みにくくならないようにするため。この空行にはコメントは要らない。
- **意味の区切り。** 1行の文どうしを、意味のまとまりで分けるときは、空行で区切り、まとまりの先頭にコメントを書く。
- テストの準備・実行・確認の区切りと、JSX の中の区切りは、コメントなしでよい。

  ```ts
  // 保存済みの値を取得するまでは、何も描画しない。
  if(settings === undefined) return undefined;

  const root = document.getElementById("root");
  if(root === null) throw new Error("描画先の要素（#root）がありません。");

  createRoot(root).render(
    <StrictMode>
      <OptionsPage settingsStore={new SettingsStore()} />
    </StrictMode>,
  );
  ```

## JSX の形
- 属性の値は二重引用符（`"`）で書く。文字列の値を `{"…"}` で囲まない。
- 開くタグに属性が2つ以上あって複数行になるときは、属性を1行に1つずつ書く。最初の属性も、タグ名の次の行から始める。
- 閉じるかっこ（`>`・`/>`）と閉じるタグは、開くタグの行頭とそろえる。
- 中身のない要素は `<X />` と書く（`/` の前に空白を1つ）。
- 子要素が2つ以上あるときは、1行に1つずつ書く。子要素が1つなら、同じ行に書いてよい。
- 複数行の JSX を返したり代入したりするときは、`(` の後で改行して囲む。

  ```tsx
  return (
    <label className="flex items-center gap-2">
      <input
        id="link-highlighted"
        type="checkbox"
        checked={settings.isLinkHighlighted}
      />
      <span>{getMessage("optionsLinkHighlighted")}</span>
    </label>
  );
  ```

- JSX の中の三項演算子も、ほかの所と同じくかっこで囲む（`className={(failed ? "text-danger" : "text-ink-muted")}`）。
- JSX の中のコメントは `{/* … */}` で書く。

## 見た目（Tailwind CSS）
- 見た目は、部品の JSX に Tailwind のクラスで書く。画面ごとの CSS ファイルは作らない。見た目と部品を同じ場所で読めるようにするため。
- 色は、この拡張機能の色（`src/style/app.css` の `@theme`。`text-ink`・`bg-paper`・`text-accent`・`text-danger` など）を使う。Tailwind の既定の色（`text-red-600` など）は直に使わない。色の決まりを1か所で変えられるようにするため。
- ダークモードは、色の変数そのものを差し替えて合わせる。部品には `dark:` を書かない。
- 新しい色が要るときは、`@theme` とダークモードの両方に足す。
- 両方の画面で同じ見た目の部品（ボタンなど）は、クラスの並びを写して使わず、React の部品にする（`src/base/Button.tsx`）。
- `@apply` は、`app.css` の土台（`body` など、JSX で書けない所）だけで使う。
- コンテンツスクリプトでは Tailwind を読み込まない。土台の CSS が、ほかのサイトのページの見た目を崩すため。ページに出す CSS は、名前がぶつからないように、拡張機能の名前を頭に付けた属性や変数で書く。

## 名づけ
- 派生した値は、名詞の関数にする（`layoutSummary` など）。
- 作成は `createXxx`、取得は `getXxx`、変換は `toXxx` にする（`createMessenger`・`getPaperSize`・`toSettings` など）。
- 真偽の値は `isXxx`・`canXxx`・`hasXxx` にしてよい。HTML の属性に合わせる部品の引数（`disabled`・`selected`・`open`）は、形容詞のままでよい。
- 1つの値を編集する部品の引数は、`value` / `onChange` にする。そのほかの知らせは `onXxx` にする。
- 画面の文言とコードの言葉をそろえる。

## 共通化
- **意味として同じものだけをまとめる。** 判断の基準は、「片方を変えたら、もう片方も必ず変えるか」。変えるなら同じ概念なので、その概念の持ち主の所に1つだけ置く。今たまたま同じ形なだけなら、まとめない。
- 置き場所は、その概念を使う範囲と、そこから見える範囲が一致する所にする。都合で下の層に押し込まない。
- React に依存しない計算は、部品のファイルから分けて置き、関数のテストで確かめる。

## 依存
- 基礎的なライブラリ（広く使われ、保守が続いているもの）は使ってよい。
- 小さな仕組みは、自分で作ってもよい。ライブラリを入れても短くならないものは、自分で作るほうが読みやすい。

## コミット
- メッセージは日本語で短く書く（20文字以内を目安）。本文は付けない。
- 内容が別なら、分けてコミットする。

## 機械で確かめる範囲
`npm run lint`（ESLint）で、次の決まりを確かめる。設定は `eslint.config.ts` にある。

- default export の禁止（設定ファイルと `src/wxt` は除く）
- `const f = () => {}` の禁止（`func-style`）
- `as`（`as const` も含む）と `!` の禁止
- `import type` の書き方・import の順番・import の後の空行
- クラスの継承・メソッドの禁止と、`public` などの修飾子
- 型引数の名前（`T` で始まる2文字以上）
- 演算子を行頭に置くこと・複数行の三項演算子・オブジェクトのプロパティの改行
- 波かっこの位置（Allman）・`if(` や `catch(` の空白・波かっこを省ける if・空行の数・見た目の区切りの空行
- 置き場所の向き（`src/util` から `src/base`、`src/base` から `src/wxt` を読み込まない）
- JSX の形（引用符・属性の改行・閉じるかっこの位置・子要素の改行・複数行のかっこ）
- React のフックの決まり（早く抜けた後や条件の中で呼ばない・依存の配列の書き漏れ）

三項演算子をかっこで囲むこと、区分の見出し、JSDoc の中身、名づけ、名前空間で読み込むかどうか、副作用だけの import の位置、意味の区切りのコメント、`switch` の `case` に付けた波かっこの位置、Tailwind の色の使い方は、機械では確かめられない。
波かっこを省いた if が「きわめて単純」かも、1行に収まるかと中身の文の種類までしか確かめない。書くときと読むときに人が気をつける。
